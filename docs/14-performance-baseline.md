# 성능 기준선 (W-28, 2026-11-14)

- 상태: **1차 기준선 측정** — 실제 AI provider·대규모 데이터는 미측정
- 스크립트: `scripts/bench.mjs` (`npm run bench`)
- 목적: 서버·PostgreSQL 경로의 병목을 조기에 찾고, 이후 비교 가능한 기준을 남긴다.

## 1. 방법

| 항목 | 값 |
| --- | --- |
| 환경 | macOS, Node 26, Docker PostgreSQL 17 + pgvector |
| 데이터 | 사용자 1명, 대화 120건(각 2 세그먼트·1 인물·1 녹음 연결) |
| 동시성 | 20 |
| 시나리오 | 각 3초 + 워밍업 10회 |
| AI | `FakeAiPipeline` (실제 provider 지연 제외) |
| 측정 | loopback HTTP, TLS/프록시 없음, 단일 API 프로세스 |

```bash
DATABASE_URL=postgres://gyeol:gyeol@localhost:5433/gyeol \
GYEOL_STORE=postgres npm run bench

# 규모/시간 조정
BENCH_CONVERSATIONS=1000 BENCH_CONCURRENCY=50 BENCH_DURATION_MS=10000 npm run bench
```

- D-07 결정(ADR-0013)에 따라 trigram + HNSW top-K 로 쿼리를 재구성해 검색 p95를 175ms로 낮췄다.

## 3. 해석

- 120건 규모에서는 DB 경로가 병목이 아니다. p95 가 모두 20ms 이하다.
- 검색은 `ILIKE` + 임베딩 조인을 사용한다. 데이터가 커지면 **전문검색 인덱스(D-07)** 와
  pgvector HNSW(`ENV-07`)가 필요하다. 현재 수치는 상한 성능이 아니다.
- 분석은 비동기 작업 큐다(ADR-0007). API 요청 지연에 실제 AI 시간이 포함되지 않는다.
  실제 provider 지연은 `analysis_jobs` 처리 시간으로 별도 측정해야 한다(ENV-05).
- 로컬 loopback·단일 프로세스이므로 네트워크·다중 인스턴스 비용은 빠져 있다.

## 4. 잠정 목표 (승인 전)

| 항목 | 잠정 목표 | 근거 |
| --- | --- | --- |
| 목록·상세 p95 | ≤ 150ms (동시성 20) | 현재의 10배 여유 |
| 키워드 검색 p95 | ≤ 250ms (동시성 20) | 인덱스 도입 전 여유 |
| 오류율 | 0% | 계약·서버 오류 없음 |
| 분석 완료 | provider p95 + 큐 대기 ≤ 5분 | 사용자 체감 |

> 수치는 **목표 후보**다. 10,000건 측정에서 검색만 목표를 초과했다. 실제 provider 와
> 인덱스 도입 후 재측정해 확정한다.
